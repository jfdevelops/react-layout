# Write docs

React Layout docs are plain Markdown pages, grouped by framework and major
version. Pages are the only thing you write by hand. Navigation, `docs.json`, every
`meta.json` and the API reference are generated from them.

The rules a page must pass live in `docs/maintainers/content-contract.md`, and
`scripts/check-docs.mjs` enforces them. Read the contract before your first edit in a
session. This skill covers where pages go, how to write them, and how to verify them.

## Where a page goes

```text
docs/
  README.md                  repository index, the only file at the root
  framework/react/
    v4/                      current major, matching packages/core/package.json
      overview.md            top-level pages: overview, installation,
      installation.md        quick-start, typescript, devtools
      guides/*.md            how-to guides, troubleshooting, migration
      plugins/*.md           companion packages (adapters, composables)
      reference/             generated by TypeDoc and gitignored; never hand-write it
      assets/*               images only
    v3/ ... v0/              earlier majors; reference/api.md is written by hand
  maintainers/               contributor notes; never public, never linked from a page
```

- Write the change in the version directory whose release it describes. A feature
  added in 4.x goes in `v4/`. Fix an earlier major only for something wrong at that
  release.
- Never put a page at the docs root. The checker rejects every root file except
  `README.md`. When a page moves, update the links that point at it. Do not leave
  stubs behind.
- Do not hand-edit `docs.json`, any `meta.json`, or the current major's `reference/`.
  They are gitignored, and `pnpm generate-docs` rebuilds them.
- Earlier majors keep a hand-written reference at `reference/api.md`, which the
  generator never touches. Fix an API detail there directly, checked against that
  major's release tag.
- For API details, link to the reference instead of copying signatures into a guide:
  `reference/index.md` or a page under it in the current major, and
  `reference/api.md` in earlier majors.
- When a new major ships, add `framework/react/v<major>/` and move the reference path
  in `.gitignore`. Version status and install versions follow automatically from
  `packages/core`.

## Frontmatter

```yaml
---
title: Lazy loading
description: Code-split whole pages, single states and scoped content, with typed errors, retry and preloading.
order: 60
---
```

- Only `title`, `description` and `order` are allowed.
- `order` sets the sidebar position. Use steps of 10 so pages can be inserted later.
  It must be unique within the directory. Run
  `grep -h '^order:' <dir>/*.md` before choosing one.
- The title is plain text. Don't put the page's own version in it. Migration pages
  are the exception: "Migrating from v3 to v4".
- The description is one sentence saying what the reader can do with the page.

## How to write a page

The owner wants docs that are plain and easy to follow. Write them that way, not
as a copy of another project's docs.

- **No `#` heading.** The site renders the frontmatter title as the `h1`. Sections
  start at `##`, and heading levels never skip.
- **Open with one or two sentences** that say what the feature does and when to use
  it. Guides then list "In this guide you will:" with three to five verb-first
  bullets.
- **One idea per section.** Give each section a task-style heading ("Load a page
  lazily", "Choose a package"). Show the code, then explain what matters about it.
- **Prefer a table** to a paragraph that lists options, packages or terms.
- **Use callouts sparingly.** A block quote that starts with `**Note:**`, `**Tip:**`
  or `**Warning:**` renders as a callout. Use one only for a rule that is easy to
  miss, such as a precedence order or an ordering requirement.
- **End with "Next steps",** a short list of links to the pages a reader most likely
  needs next.
- **Don't name the page's own version** in the title, description or intro. The URL
  and version selector already show it. Name another version only for a real
  cross-version fact: a migration step, an "added in 4.1.0" note, or a compatibility
  table.
- **Document only what the source supports at that version.** Check the exports,
  tests and changelog before you describe an API. For an earlier major, read the
  source at that major's last release tag, not `main`. For example:
  `git show @jfdevelops/react-layout@3.3.0:packages/core/src/index.ts`.
- **Never invent dates, versions or release facts.** Take them from
  `packages/core/CHANGELOG.md`, `package.json` or the git tags.

Look at `v4/guides/lazy-loading.md` for a full guide, and at `v4/installation.md`
and `v4/plugins/adapters.md` for shorter pages.

### Code

- Every fence needs a language from the list in the contract: `ts`, `tsx`, `js`,
  `jsx`, `json`, `sh`, `bash`, `text`, `css`, `diff`, `yaml`, `npm`, `pnpm`, `yarn`
  or `bun`.
- Write examples as a reader would: import from the public package
  (`@jfdevelops/react-layout`), not from internal paths, and use realistic resource
  names such as `appointments`.
- Write each install command four times, in consecutive fences labeled `npm`,
  `pnpm`, `yarn` and `bun`, using `npm i`, `pnpm add`, `yarn add` and `bun add`.
  Development dependencies take `-D` in all four. The checker rejects install
  commands in `sh` or `bash` fences.
  - **Current major:** install unpinned, or pin a release of that major.
  - **Earlier majors:** pin every package exactly, and pin the core package to that
    major's last release, so copying an old guide never installs the latest major.
- To have an example type-checked, put the code in `tools/docs/examples/<path>` and
  mark the fence `` ```tsx example=<path> ``. The fence must match the file exactly.

### Links

- Link between pages with relative `.md` paths, optionally with a `#anchor`. Anchors
  use GitHub heading slugs.
- Cross-version links work too, for example `../../v3/migration.md` from a v4 guide.
- External links must be `https://`. Link to repository source by inline code, or by
  an `https://` link pinned to a tag.
- Never link a public page to `docs/maintainers/`, and never use an absolute `/`
  path.
- Package READMEs under `packages/*/README.md` link into the current major, for
  example `../../docs/framework/react/v4/guides/props-and-validation.md`. Update them
  when a page they point to moves.

## Verify

Run these from the repository root. All of them must pass.

```bash
pnpm generate-docs        # API reference, docs.json and every meta.json
pnpm check:docs           # frontmatter, layout, links, anchors, install pins, order
pnpm check:docs-examples  # only if you added or changed tools/docs/examples
pnpm format
pnpm lint
```

If you changed `scripts/check-docs.mjs` or `scripts/docs-manifest.mjs`, also run
`pnpm test:docs`.

Every checker error names a code, a file and a fix, so fix the page rather than the
checker. The generated reference currently has about 25 broken `-1` anchors on
inherited members. These come from typedoc-plugin-markdown, not from your page.

After formatting, run `git status`. If a file you did not edit shows up with only
line-ending changes, restore it rather than committing it.

## Commit

- Follow the repository's git conventions (the `jf-git` skill). Use
  `docs(<scope>): <subject>`, for example `docs(react): add lazy loading guide`.
- A docs-only change needs no changeset. CI checks changesets only when a pull
  request adds one or changes a non-Markdown file under `packages/`.
